## 背景：这个项目大致是什么

MuJoCo 里仿真一个 Franka Panda 机械臂打磨一个"半平面半圆弧"的工件表面。控制器是阻抗控制 + 显式力控制的混合结构，最近一次大改是把力控制和运动跟踪从"世界坐标系（z轴/xy平面）"改成了"表面局部坐标系（法线方向/切平面）"，法线来源于一个真实的深度相机点云感知管线（不是读取工件设计公式作弊）。这些内容教材里都写了，如果需要完整背景应该先读 `notes/mujoco_polishing_textbook.md` 第五、七、十二章。

## 本次会话做了两件事

### 一、点云感知的噪声鲁棒性测试

**动机**：用户指出仿真里的深度相机渲染太干净了（MuJoCo 的 `Renderer` 本身不带噪声），现实中的深度相机没这么理想，需要测试点云变差之后系统还稳不稳。

**发现的关键现象——不是"变差"，是"断崖式失效"**：

给点云重建出的点的 z 坐标加入模拟的高斯噪声（代表深度传感器噪声），测试法线拟合精度（`fit_normals_along_x()` 拟合出的法线 vs 解析真值的角度误差）：

| 单帧噪声标准差 | 拟合角度误差 |
|---|---|
| 0~2mm | 几乎不受影响（<0.2°） |
| 5mm | 明显退化（均值 5°，最大 14°） |
| **7mm** | **几乎每个窗口都错**（均值 49°，最大 86°），打磨头直接失去接触 |

**根因**：`fit_normals_along_x()` 每个 x 窗口宽 `SCAN_BIN_HALF_WIDTH*2 = 24mm`，窗口内点在 x 方向天然散布的标准差约为 `24mm/√12 ≈ 6.9mm`。一旦深度噪声接近这个数量级，SVD 平面拟合分不清"哪个方向散布最小"（z 方向的噪声散布和 x 方向的窗口宽度散布变得同量级），拟合出的法线会在 x 轴和 z 轴之间随机跳。**这不是异常点问题，是几乎每个窗口都会犯错的系统性歧义**。

**试过的修复方法**：
- ❌ 跨窗口做中位数滤波（假设是"少数窗口坏、多数窗口好"）——测试后**没用**，因为噪声大到临界点时是"几乎所有窗口都坏"，中位数滤波在这种情况下无能为力。
- ✅ **多帧平均**（模拟真实深度相机内部做的时序降噪）——有效。噪声按 `√帧数` 下降，测试确认：无论原始单帧噪声多大，只要平均足够多帧、把"等效噪声"压回 2mm 以内，精度就能恢复到几乎无损（具体数据见下面的代码注释）。

**已经落地到代码里的改动**（`polish_impedance_control.py`）：
```python
DEPTH_NOISE_STD = 0.002   # 第 244 行附近，模拟真实深度相机噪声（2mm）
SCAN_NUM_FRAMES = 4       # 第 260 行附近，平均 4 帧模拟时序降噪，等效噪声再打对折
```
`capture_point_cloud()`（约第 264-291 行）现在会对渲染出的深度图注入 `SCAN_NUM_FRAMES` 次独立噪声再取平均，而不是直接用 MuJoCo 渲染出的"完美"深度图。**已验证**：加上这两个改动后，跑一遍完整仿真，力误差跟改之前基本一致（约 0.25N），没有引入退化。

**尚未做但可能有用的后续**：
- 这个"7mm 是临界点"的发现值得写进教材（目前教材第十二章还没提这件事）。
- 如果想要更大的噪声容忍度，还可以考虑加大 `SCAN_BIN_HALF_WIDTH`（但会牺牲 x 方向的曲率分辨率，是个权衡，没有测试过具体数值）。

### 二、力的安全上限机制

**动机**：用户提出"输出的力最好不能大于期望值，因为打磨少了没事，打磨多了可能出问题"，希望有个安全上限。

**第一版方案（已实现，但用户指出理解不够，且不够好）**：`F_MAX = F_TARGET + 1.0 = 9.0N`，对**控制器命令的力**（`Fn_cmd`）做硬限幅：
```python
Fn_cmd = max(Fn_cmd, -F_MAX)
```
测试发现一个反直觉的结论：**把上限直接设成等于目标值（`F_MAX=F_TARGET`，零余量）反而更差**——测出来的噪声/极差不降反升（std 从 0.318N 升到 0.347N，极差从 2.61N 升到 3.48N），因为力环需要一点"多推一把"的余量才能收敛，完全砍掉这点余量会让抖动变大。留 1N 余量（9.0N）不影响正常表现（正常情况下命令值到不了这个上限），但能在异常时把命令值卡住。

**这版方案的局限（用户指出后进一步改进）**：`F_MAX` 卡的是"控制器打算命令多大力"，不是"实际测到的接触力"——两者中间隔着机械臂动力学、接触刚度。压力测试证实：用很差的点云噪声测试时，即使命令值被 `F_MAX` 卡住，真实测到的力还是能冲到 10.2N，超过了 9.0N 这个"软上限"。

**第二版方案（用户提出，已实现并验证有效）**：用户提出双滤波 + 安全跳闸的思路——用一个慢滤波信号做常规控制、一个快滤波信号专门做安全监控，两者互不干扰。已实现（约第 101-113 行定义常量，第 407 行初始化状态，第 440-450 行触发逻辑，第 483-490 行 retreat 行为）：

```python
F_FAST_ALPHA = 0.2         # 快滤波，专门用于安全监控，不参与常规力控制
F_RETREAT_TRIGGER = 25.0   # N，快滤波信号一旦超过这个值就触发紧急撤离
F_RETREAT_CLEAR = 1.5 * F_TARGET  # N，滞回下限，避免在临界点反复触发/解除
F_RETREAT_FORCE = 20.0     # N，撤离时沿法线方向拉开的固定力（不是PI，是钝力）
```
每步循环里：
```python
f_fast += F_FAST_ALPHA * (f_n_raw - f_fast)          # 快滤波，独立于 f_filt
if not retreating and f_fast > F_RETREAT_TRIGGER:
    retreating = True
elif retreating and f_fast < F_RETREAT_CLEAR:
    retreating = False
    f_integral = 0.0                                  # 恢复时清空力积分，避免带着旧误差冲回去
...
if retreating:
    F_xyz = F_RETREAT_FORCE * n   # 撤离：忽略PI力控和光栅轨迹，直接沿法线拉开
else:
    ...（原来的法线力控 + 切平面阻抗）
```

**已验证**：
1. 正常配置（`F_TARGET=8.0`，`F_MAX=9.0` 开着）下跑一遍，结果跟之前一致（约 0.25N 误差），没有破坏任何东西。
2. 单独把触发阈值临时调低（测试用，非正式参数）后，能清楚看到触发→力被拉到接近 0→满足解除条件后尝试恢复的完整过程——机制本身工作正常。

**发现的问题（尚未修复，需要下一步讨论决定怎么处理）**：

1. **`retreat()` 只能应对"瞬时冲高"，应付不了"持续性故障"。** 测试时故意制造了一个不会消失的故障（把 `F_TARGET` 硬改成 40N 且关掉 `F_MAX` 来复现"某个环节持续出错"的场景），发现：一旦退开、力降下来、`retreating` 被清除，控制器立刻恢复正常逻辑，而故障源头没消失，于是几乎立刻又想猛推、又被拦下，如此反复，系统卡在"退开→冲回去→又被拦下"的死循环里，实际打磨完全停滞。**这个问题只在人为制造的极端场景里出现，当前生产配置（`F_TARGET=8.0` + `F_MAX=9.0`）不会碰到**，因为 `F_MAX` 已经先把命令值摁住，到不了触发 retreat 的量级。但如果以后 `F_TARGET` 改大、或 `F_MAX` 被去掉/调松，这个死循环隐患是存在的。合理的修复方向是加一个"重试次数计数器"：短时间内触发次数超过某个阈值就**锁死**（停止尝试恢复，报故障，等人工干预），而不是无限重试——类似工业上"瞬时过流保护自动复位，重复跳闸就该锁定报警"的逻辑。**这个加固逻辑还没写进代码**。

2. **`F_RETREAT_TRIGGER=25N` 这个数可能设得太高，实际永远触发不到。** 压力测试发现：就算故意制造最坏情况（点云噪声很差 + `F_TARGET=40` + 关掉 `F_MAX`），机械臂实际能压出来的真实力也就卡在 14-19N 左右，很难摸到 25N——因为机械臂本身的关节力矩上限（`ctrlrange`，见 `panda_torque.xml`）已经是一道物理天花板。这提示 25N 这个阈值在**这套具体的机器人+任务**上可能永远触发不到，形同虚设，需要降低（比如降到 15-18N）才能真正起到保护作用。**这个数值还没有改**，需要先讨论想要多大的安全边际再定。
